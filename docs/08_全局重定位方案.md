# 08 全局重定位方案（FAST-LIO 载图定位）

更新时间：2026-08-29。选型调研 + 接入设计。狗未上电时段完成，全部为
离线分析；落地需要上电后验证。

## 为什么需要

FAST-LIO 每次上电都把当前位置当 `camera_init` 原点，导致：

1. 上次建的地图、巡查点坐标全部失效，每次开机都要重新建图；
2. 巡检系统无法"在已知地图里定位自己"，断电/重启后巡检任务中断；
3. OOM 重启后连"回到出发点"都做不到。

## 现状盘点（2026-08-29 实查）

| 项 | 现状 |
|---|---|
| FAST_LIO_ROS2 | Ericsii 的 FAST-LIO2 ROS2 移植，**纯里程计**，无载图/重定位 |
| 地图文件 | `maps/` 为空，从未存过图（`pcd_save_en: false`） |
| 存图能力 | **已有现成服务** `ros2 service call /map_save std_srvs/srv/Trigger`，写入 `map_file_path`（= `/project/maps/mid360_map.pcd`，camera_init 世界系） |
| 可用话题 | `/cloud_registered`（世界系稀疏点云，20Hz）、`/Odometry`——重定位所需输入**全部现成** |
| 定位包 | 无，零基础 |

注意：Ctrl+C 退出时还会往 `FAST_LIO_ROS2/PCD/scans.pcd` 存一份（源码
main() 里写死），与 `/map_save` 服务无关；**OOM kill -9 时两份都不会
存**，所以长时间建图要定期调 `/map_save`。

## 推荐方案：myeongw002 移植版接入现有栈

三个 Python 节点，与现有 FAST-LIO **同域（42）直接对接，零 remap**：

```text
global_map_publisher   读 /project/maps/mid360_map.pcd → 发布 /global_map
global_localization    订阅 /global_map + /cloud_registered + /Odometry
                       订阅 /initialpose (PoseWithCovarianceStamped, RViz 2D
                       姿态估计或 web 端发布) → Open3D ICP 初始对准
                       之后 1Hz 持续 ICP → 发布 /map_to_odom
transform_fusion       融合 /Odometry(高频) + /map_to_odom(低频)
                       → 动态 TF map→camera_init（50Hz）
                       → /localization（map→body 里程计）
```

规划栈不用动：它继续工作在 camera_init 系，只是现在这个系被 TF 锚定到
了 map 系。**巡查点、巡查路线从此全部存 map 系**，跨开机有效。

### 必改点（接入时做）

1. **TF 冲突（最重要的坑）**：规划栈 launch 里的静态恒等 TF
   `map→camera_init`（terrain_analysis frame_id 补丁）会和重定位的动态
   TF 打架。给 launch 加 `use_static_map_tf` 参数：建图模式 true，
   定位模式 false。
2. **global_map_publisher 的 interval**：默认每 5s 重发整幅地图点云
   （数百万点），CPU/带宽浪费大。global_localization 收到第一帧就退订
   了，所以改成**只发一次**（或 interval 调大）。
3. **Open3D 装进容器**：`pip install open3d`（wheel 约 100-400MB）。
   global_localization.py 逐点 `for x,y,z in pc2.read_points(...)` 的
   Python 循环换成 numpy 一次读出（顺手优化）。
4. 存图脚本 `scripts/save_map.sh`：调 `/map_save` 服务 + 校验文件大小。

### 内存预算（5.7GB 机器）

| 项 | 估计 |
|---|---|
| 现有建图栈 | 已实测 1.7GB（含系统） |
| FAST-LIO 地图增长 | 不受限，持续涨（OOM 根因，另案处理） |
| open3d 运行时 | ~300-500MB |
| 全局地图（0.5m 体素，室内外一座楼规模） | numpy 点集 ~100-300MB + ICP KDTree ~200MB |
| **结论** | 可行，但建图时间要控制；定位模式建议不建图（纯定位） |

## 巡检工作流（目标态）

```text
建图（一次性）：
  上电 → 建图模式跑起来 → 遥控走一圈覆盖巡检区域
  → ros2 service call /map_save std_srvs/srv/Trigger
  → maps/mid360_map.pcd

巡检（每次开机）：
  上电 → 定位模式（载图，不建图）
  → 把狗推/走到已知出发点附近，RViz 或 web 点一下初始位姿
  → ICP 初始定位成功（看 fit score）
  → 持续重定位运行，巡查点(map系) 下发 /goal_point
  → 规划栈、运动桥全部照旧
```

## 风险

1. **初始位姿偏差太大 ICP 对不准** → 流程上要求从已知点出发；fit score
   （`localization_th: 0.9`）不合格就不初始化，宁可不定位也别错定位。
2. **长走廊/开阔室外退化**：几何特征少时 ICP 滑动。表现是
   `/map_to_odom` 漂移——先用 fit score 监控，二期上 ScanContext。
3. **建图时间过长** → OOM 且图大。建议分段建多张图 + 后期合并
   （open3d 可以做），单图控制在 20-30 分钟内。
4. Python ICP 在 1Hz 下 CPU 占用需实测，超预期就把 `freq_localization`
   降到 0.5Hz。

## 落地验证步骤（上电后）

1. `pip install open3d` 进容器，克隆 myeongw002 仓库到 ros2_ws，colcon
   单包编译（`--parallel-workers 1`）。
2. 打开 `pcd_save_en: true`，建图模式跑 10-20 分钟小图，调 `/map_save`，
   检查 `maps/mid360_map.pcd` 大小（预期几十 MB）。
3. 重启为定位模式：载图 → RViz 点初始位姿 → 确认
   `Global map received` → `Initial global localization succeeded`。
4. 观测：`/map_to_odom` 的 fit score、TF map→camera_init 是否稳定、
   CPU/内存增量。
5. 漂移测试：狗走 10m 折返，看 `map` 系位姿是否回到出发点
   （合格线：误差 < 0.3m，与路径起点校验阈值一致）。
